    aifw command reference¶

    aifw installs and operates the whole server. It is the only supported way to install the server. The sequence is:

    sudo bash install.sh     # installs the aifw command (see "The installer script")
sudo aifw setup          # installs and configures the server

    Find your command in the summary table, then read its section. Every command is run with sudo.

    Before you start¶

    • Access: SSH to the server, and an account that can use sudo.
    • The aifw command is installed: install.sh has finished with "Next step: sudo aifw setup". See The installer script.
    • The registry is reachable: versions, setup and upgrade need to reach the software registry. The other commands work offline.

    Summary¶

    Group Command What it does Changes the server?
    Before you install or upgrade aifw versions Lists the server versions available to install No
    Setting up and repairing aifw setup Sets up the server, guided Yes
    aifw setup --check Shows what setup would do No
    aifw setup --answers <file> Sets up with no questions, reading answers from a file Yes
    Moving to a newer version aifw upgrade [--version <v>] Moves the server to a newer version. Backs up first, keeps data Yes
    Checking a running server aifw status Is everything healthy? No
    aifw security-audit Checks the security posture No
    aifw doctor A full check-up with numbered findings and fixes No
    Backing up aifw backup Backs up the database and settings now Yes (adds files only)
    The tool itself aifw --version Prints the version of aifw No
    aifw --help Prints the help (also what you get with no arguments) No
    aifw preflight The machine checks on their own. setup runs them for you No

    The marks in the output are the same everywhere: ✓ passed, ! a recommendation, ✗ a requirement that is not met.

    aifw versions¶

    Lists the versions that the software registry holds, newest first. Changes nothing.

    A version that is not in the list cannot be installed or upgraded to. If the version you need is missing, it has not been published yet: wait for it, or contact support. Older versions stay in the list and stay installable.

    # aifw versions
Available server versions (newest first):
2.2.6
2.2.5
2.0.75

    aifw setup¶

    Run this after install.sh has finished. It performs the installation, and it is also the repair command.

    The order:

    1. The questions. It asks for the server type, the public address, how HTTPS works, the version, whether the emergency token field appears on the sign-in page, the license file, your email, the name of the first workspace, and an optional limit on SSH addresses. It then prints the answers back and asks for a yes. Nothing on the server has changed yet.
    2. The machine checks. If a requirement is not met, setup stops and prints what to fix. Nothing has changed yet.
    3. The phases, one at a time, printing each step as it runs.
    4. The security posture. The checks that did not pass, each with a fix. The installation has already succeeded. These are open items, not failures.

    Running it again is safe. Each step looks at the server before it changes anything, so a second run changes only what has drifted. The questions offer your previous answers.

    setup is the only command that configures the sign-in service. When a check says the administrator sign-in failed, run sudo aifw setup. An upgrade does not do this.

    [TBC: product team to confirm what happens when you re-run setup with a changed answer, for example another public address. The installation runbook says to restore the snapshot first.]

    Options:

    • --check prints what would change and changes nothing. Use it before a repeat run on a live server.
    • --answers <file> runs without questions, reading the answers from a file. See Install the server.

    Also: setup turns on the automatic security updates of the system.

    aifw upgrade¶

    Moves the server to a newer version. It takes a backup first, and your data stays.

    Run it without --version to take the newest published version. Run it with --version 2.2.5 to take a named one.

    Four limits:

    1. It cannot reach a version that is not published. Run aifw versions first. If the target is the version already running, it stops with This server is already on <version> — nothing to do. Nothing was changed.
    2. It does not go backwards. Database changes only move forward. A typing mistake in a version number is enough to try a downgrade, so the refusal is a stop, not a warning.
    3. It does not set up sign-in. The server keeps the sign-in setup it had. Run sudo aifw setup for that.
    4. It does not move third-party software. The database, the sign-in service, the web front end and the monitoring stay where they are. They move when the product pins newer versions of them.

    The run ends with the security posture, the same list that security-audit prints.

    Upgrade the server before the agents

    Deploy the server first, or at the same time as the first agent of a new version. An older server drops the parts of a newer agent's data that it does not recognise. It can also report findings that are not findings. Nothing checks the order for you.

    Two lines are worth recognising:

    The installer updated itself — continuing the upgrade with the new version
This server is already on <version> — nothing to do

    The first means the tool replaced its own program and ran once more. That is normal. The second is a success: nothing newer is published.

    Checking a running server¶

    Three commands, three questions:

    • aifw status: is the server working?
    • aifw security-audit: is it safe?
    • aifw doctor: both, plus the machine checks, with a fix beside each finding.

    aifw status¶

    Reports whether the server is working. Changes nothing.

    It runs the health checks that the stack performs on itself, then prints the services, the free disk space, the age of the last backup, whether the sign-in address matches the configuration, and how long the web certificate is still valid.

    One health check would create a workspace. status skips it and says so.

    # aifw status
Server status:
Server check:
✓ Server configuration present
✓ All services running — 7 services up
✓ Health checks — PASSED: 24 FAILED: 0
✓ Free disk space — 81 GB free
✓ Recent backup (under 26 hours old) — backup-2026-09-30T00-27-04.sql.gz, 7.3 h old
✓ Sign-in service address matches the configuration
✓ Web certificate validity — expires in 633 day(s)

    aifw security-audit¶

    Reports the security posture. Changes nothing.

    It checks the firewall, file permissions, license enforcement, demo accounts, the stored registry sign-in and pending system updates.

    The last line says This server is not ready yet in two different cases: a posture that is not hardened, or a check that could not run at all. The ✗ rows say which. could not check means nothing is known either way. It is not a pass.

    Abridged example. The long "What to do" texts are shortened:

    # aifw security-audit
Security posture:
Server check:
✓ Server configuration present
✓ Firewall enabled, incoming denied by default
! SSH password sign-in disabled (keys only)
What to do: Consider key-only SSH …
! SSH reachable only from addresses you trust — port 22 accepts connections from any address
What to do: Restrict SSH to the addresses your administrators use …
✓ Configuration and credentials are administrator-only
! Credentials sheet moved to a password manager — credentials.txt still on the server
What to do: Move its contents to your password manager, then delete credentials.txt.
✓ License enforced with the built-in verification key — license active
✓ Registry sign-in — this must be a READ-ONLY access token, never a publishing one
✗ No demo accounts in the sign-in service — could not check
What to do: This check could not run, so nothing is known either way …
! System packages current — 10 update(s) pending
What to do: Automatic security updates are on; a reboot may be needed …
This server is not ready yet: 1 requirement(s) unmet, 4 recommendation(s).

    aifw doctor¶

    Runs everything that status and security-audit run, plus the machine checks. Prints the result as numbered findings, each with its fix. Changes nothing.

    Run it when something is wrong and you want a list of actions, or when you do not know which of the three to use.

    aifw backup¶

    Dumps the database and the settings. The database of the sign-in service is included. Dumps older than 30 days are deleted.

    Set AIFW_BACKUP_REMOTE and the dump is also copied off the machine. setup installs a timer that takes a backup every day. upgrade takes one before anything moves. Run the command by hand before a risky change.

    It adds files and deletes its own old dumps. Nothing else is written.

    # aifw backup
Backing up the database (this can take a minute)...
Note: backups live only on this server. An off-server copy protects against losing the machine.
Backup done: /opt/ai-firewall/backups/backup-2026-10-06T08-45-59.sql.gz (0.1 MB)

    The note appears when AIFW_BACKUP_REMOTE is not set. A settings file is written beside the dump with the same time stamp. See Backup and restore for what else to save and how to restore.

    The tool itself¶

    aifw --version¶

    Prints the version of the aifw program on this machine. That is not always the version the server runs: the two drift apart when the program is left behind. An old program then reports services as missing, because it looks for containers that a newer stack has retired.

    # aifw --version
aifw 2.2.6

    aifw --help¶

    Lists every command with a one-line description. aifw with no arguments prints the same.

    aifw preflight¶

    Runs the machine checks on their own, without starting an installation. Changes nothing. setup runs the same checks as its first step and stops if a requirement is not met, so there is rarely a reason to type it. On a running server, doctor includes it.

    It checks: administrator rights, machine type, operating system, number of processors, memory (4 GB minimum, 8 GB recommended), free disk space (20 GB minimum), systemd, Docker installed and running, Docker Compose, whether the registry can be reached, and ports 80, 443 and 8090.

    # aifw preflight
Server check:
✓ Administrator rights
✓ Machine type — this machine is x86_64
✓ Operating system — Ubuntu 24.04.5 LTS
✓ Processors — 2 available
✓ Memory (minimum 4 GB) — 7.8 GB installed
✓ Memory (recommended 8 GB) — 7.8 GB installed
✓ Free disk space (minimum 20 GB) — 82 GB free
✓ Service manager (systemd)
✓ Docker installed and running
✓ Docker Compose available
✓ Software registry reachable
✓ Web ports free (80, 443, 8090)

    On a server that is already running, the ports check recognises the product's own services and names them. A ports warning means another program holds the port.

    If something goes wrong¶

    Symptom Likely cause What to do
    setup stops on the server check, before asking anything The machine is short of memory or disk, or cannot reach the registry Each ✗ row names the fix. Nothing was changed. Fix it, then run sudo aifw setup again
    The chosen version does not exist in the registry That version was never published Run aifw versions. It lists everything that can be installed
    This server is already on a version — nothing to do upgrade resolved to the version already running Nothing is wrong. The newer version is not published yet
    The version is OLDER than the version this server runs A downgrade, usually a typing mistake Check the version. Do not force it
    A check warns that port 80, 443 or 8090 is in use A program other than the product holds the port Find out which program before you continue
    security-audit says the server is not ready, but it looks healthy The sign-in posture is not hardened, or could not be checked Read the ✗ rows. For could not check, run sudo aifw setup so the sign-in steps are applied
    setup or upgrade ends with security items it never showed before The run prints the posture now. Older versions did not Nothing broke. The items were always there
    A service is reported as not running, but the stack looks fine The installed aifw expects a container that the current stack no longer has Compare aifw --version with the version of the stack. An old program reports containers that a newer stack removed on purpose
