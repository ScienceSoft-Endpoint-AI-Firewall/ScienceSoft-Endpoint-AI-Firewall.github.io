    Backup and restore¶

    This page explains what to back up, how to make a backup, and how to bring the server back from one.

    Never run docker compose down -v on a server

    It deletes the data volumes, including the database. Use docker compose stop or down without -v. Nothing on this page removes a volume.

    Restore is a manual procedure

    On a terminal, aifw backup opens a menu with Backup and Restore. The manual steps below show what a restore does and cover a move to a new server. They have been proven only in part. Rehearse the whole procedure on a test server before you rely on it.

    What holds your data¶

    What Where What it holds Priority Saved by aifw backup
    Database ai_firewall volume pg-data Workspaces, devices, enrolment keys, policies, admin users, audit records and their chain, conversations, statistics Critical Yes
    Database keycloak the same volume People, groups, one-time codes, clients and the signing keys of the sign-in service Critical Yes
    Database roles the same volume The database accounts and their password hashes Critical Yes
    The settings file .env docker/.env in the install folder Every credential and shared secret of the server, the license, the image versions, the public address Critical A copy is kept on the server only
    Captured data volume capture-data Per-workspace capture data and approved destinations High No
    Generated briefs volume briefs-data Generated discovery files Medium No
    Policy presets, secrets folder presets/, secrets/ in the install folder Policy presets, optional secret files High No
    Your own TLS certificate docker/caddy/certs/ The certificate and key, if you chose your own certificate Medium. A Let's Encrypt certificate can be issued again No
    Installation files the install folder provision-manifest.json, credentials.txt if you kept it, proxy-snippets/ Medium No
    Registry sign-in /root/.docker/config.json The access that lets aifw upgrade download images Medium. It can be issued again No
    Metrics volumes prometheus-data, grafana-data Metrics for 30 days and dashboard settings Low No

    What you do not need to back up: the containers (they are rebuilt from the images), the device certificates and private keys (they exist only on each computer; the server keeps public keys only, and these are in the database), and encryption keys (the server has none).

    Why .env must travel with the database¶

    A database dump alone cannot be restored into a working server. The dump restores the database account password hashes, and the passwords in .env must match them. The keys of the sign-in service and the shared secrets in .env must match the restored database too. Keep the .env copy as carefully as a password vault. It holds every credential of the server.

    Make a backup¶

    All commands run on the server, with sudo.

    What aifw backup does¶

    sudo aifw backup
    1. Dumps both databases and all roles into /opt/ai-firewall/backups/backup-<time>.sql.gz. A failed or empty dump is deleted, and the command fails.
    2. Copies docker/.env to /opt/ai-firewall/backups/backup-<time>.env, readable by the administrator only.
    3. Deletes its own backups older than 30 days.
    4. If AIFW_BACKUP_REMOTE is set, copies only the .sql.gz file to that place with scp. A failed copy shows a warning.

    The .env copy stays on the server. Move it to your backup storage yourself.

    aifw upgrade makes the same backup before it changes anything, and stops if the backup fails.

    Set it up once¶

    1. Choose a place outside the server. Add this line to /opt/ai-firewall/docker/.env, and make sure the administrator's SSH key is allowed on that machine:

      AIFW_BACKUP_REMOTE=<user>@<backup-host>:/path/to/backups/

    2. Turn on the daily schedule. Setup already does this. To install it again:

      sudo aifw backup --install-timer
systemctl list-timers aifw-backup.timer

      It runs once a day, with a random delay of up to an hour, and catches up after a restart.

    3. Run a first backup now, and look at the result:

      sudo aifw backup
ls -lh /opt/ai-firewall/backups/

    Save what aifw backup does not¶

    Copy the volumes and files from the table above, and move the .env copy and the archives off the server.

    STACK=/opt/ai-firewall/docker
BK=/var/backups/ai-firewall/$(date +%F_%H%M)
sudo mkdir -p "$BK" && sudo chmod 700 "$BK"

# the data volumes
for v in capture-data briefs-data; do
  sudo docker run --rm -v ai-firewall_${v}:/data:ro -v "$BK":/backup debian:stable-slim \
    tar czf /backup/${v}.tgz --numeric-owner -C /data .
done

# configuration, the compose files, and the installation files
sudo tar czf "$BK/files.tgz" -C "$STACK" presets secrets caddy
sudo cp "$STACK"/docker-compose*.yml "$BK"/
sudo tar czf "$BK/install-files.tgz" -C /opt/ai-firewall provision-manifest.json proxy-snippets

    Then copy $BK and the .env copy to storage outside the server.

    Check that a backup is good¶

    Check Expected
    The .sql.gz file Not empty, and gunzip -t finds no error. zgrep -c 'CREATE DATABASE' shows at least 2
    The .env copy Present, readable by the administrator only
    The archives tar tzf lists the files without errors
    The copy outside the server Exists and is complete
    How fresh it is sudo aifw status and sudo aifw doctor warn when the newest backup is more than 26 hours old, or empty
    A restore drill A recent dump loads into a throw-away PostgreSQL 16 container with no errors except "already exists"

    Restore¶

    Before you start¶

    • Use the same or a newer version. The database is upgraded on start. A version older than the dump is not supported. The version is in the .env copy.
    • Keep the same public address. The address is stored in the database, in the sign-in service and in .env, and the agents have it in their settings. Changing it is not covered here.
    • The order matters. Load the databases before the sign-in service and the server start against them. Otherwise the sign-in service creates a new empty realm, and the server migrates an empty database. Setup and upgrade start everything at once, so load the database by hand.
    • You need: the database dump, the .env copy, the volume and file archives, and the registry access details from your welcome email.

    Variables used below:

    STACK=/opt/ai-firewall/docker
BK=/path/to/the/unpacked/backup
COMPOSE="docker compose --project-directory $STACK --env-file $STACK/.env -f $STACK/docker-compose.prod.yml"
# with bundled HTTPS, add:  -f $STACK/docker-compose.tls.yml
PG_USER=ai_firewall        # or the PG_USER value from the .env copy

    Scenario A: a new server¶

    1. Prepare the server. Ubuntu 24.04, the same network rules as the old one. Install the same version of the setup tool with install.sh.

    2. Put the .env back before you run setup. Setup never rewrites an existing .env. It only adds missing keys.

      sudo mkdir -p /opt/ai-firewall/docker
sudo install -m 600 "$BK"/backup-*.env /opt/ai-firewall/docker/.env
sudo tar xzf "$BK/files.tgz" -C "$STACK"
sudo cp "$BK"/docker-compose*.yml "$STACK"/
sudo tar xzf "$BK/install-files.tgz" -C /opt/ai-firewall

      The compose files (docker-compose.prod.yml, and docker-compose.tls.yml for bundled HTTPS) are not part of aifw backup. On a new server they exist only after setup has run, so step 4 needs the copies that you saved.

    3. Sign in to the registry with the access details from your welcome email, so the images can be downloaded. install.sh does this.

    4. Start only the database, and wait until it is ready. On an empty volume it starts, restarts once and sets itself up, so wait twice:

      $COMPOSE up -d postgres
until docker exec ai-firewall-pg pg_isready -U $PG_USER; do sleep 2; done
sleep 5
until docker exec ai-firewall-pg pg_isready -U $PG_USER; do sleep 2; done

    5. Load the dump (see Load the database dump).

    6. Restore the data volumes. Create them first, then unpack:

      $COMPOSE up --no-start
for v in capture-data briefs-data; do
  docker run --rm -v ai-firewall_${v}:/data -v "$BK":/backup debian:stable-slim \
    sh -c "tar xzf /backup/${v}.tgz --numeric-owner -C /data && chown -R 10005:10005 /data"
done

    7. Start everything, then run setup again to put back the host settings (the backup timer and the checks). It finds the existing .env and keeps it:

      $COMPOSE up -d
sudo aifw setup

    8. Point traffic at the new server. Change the DNS record, or the target of your load balancer or proxy.

    9. Check (see Check after a restore). Switch off the old server only when the checks pass.

    Images are not loaded from a file. They are downloaded from the software registry, with the registry sign-in that install.sh stored, when you run aifw setup or docker compose up.

    When you run sudo aifw setup in step 7, give the same public address, version and administrator e-mail that the restored .env holds. Setup keeps the restored .env and refuses a different address, version or e-mail. Setup writes credentials.txt again. Delete it after you save what you need.

    Scenario B: the same server, damaged data¶

    1. Take a safety dump of the current state first. It is the only way back if the restore goes wrong:

      sudo aifw backup

    2. Stop everything except the database. Do not use down -v:

      $COMPOSE stop control-plane keycloak admin-portal grafana prometheus

    3. Put back the matching .env if it changed since the backup (for example after credentials were changed):

      sudo install -m 600 "$BK"/backup-*.env "$STACK/.env"
$COMPOSE up -d postgres

    4. Load the dump (next section).

    5. Restore files and volumes only if they are damaged, as in Scenario A, step 6.
    6. Start the server with the same or a newer version: $COMPOSE up -d. Then check.

    Load the database dump¶

    The dump already holds the commands that create the roles and both databases. Remove the existing databases first, then load the dump while connected to the maintenance database:

    docker exec -i ai-firewall-pg psql -U $PG_USER -d postgres <<'SQL'
SELECT pg_terminate_backend(pid) FROM pg_stat_activity
WHERE datname IN ('ai_firewall','keycloak') AND pid <> pg_backend_pid();
DROP DATABASE IF EXISTS keycloak;
DROP DATABASE IF EXISTS ai_firewall;
SQL

gunzip -c "$BK"/backup-*.sql.gz | docker exec -i ai-firewall-pg psql -U $PG_USER -d postgres 2>&1 | tee /tmp/restore.log
grep -i error /tmp/restore.log

    Expected error: role "ai_firewall" already exists. Later lines still set the right password hash. Any other error means the restore is incomplete. Stop, find the cause, and go back to the safety dump if needed.

    Quick check before you start the rest:

    docker exec ai-firewall-pg psql -U $PG_USER -d ai_firewall -c "SELECT count(*) FROM tenants;"
docker exec ai-firewall-pg psql -U $PG_USER -d keycloak -c "SELECT name FROM realm;"

    The first must give the number of workspaces you expect. The second must list master and ai-firewall.

    Check after a restore¶

    # Check Command Expected
    1 Containers are healthy docker ps --format '{{.Names}} {{.Status}}' The database, sign-in service, portal and server are healthy
    2 The server is alive curl -fsS http://localhost:8090/health {"status":"ok"}
    3 The database is reachable curl -fsS http://localhost:8090/ready {"status":"ready"}
    4 The database was upgraded docker logs ai-firewall-control-plane 2>&1 \| grep -i migrat Pending changes applied, no failure
    5 The built-in checks sudo aifw status && sudo aifw doctor All pass, including the sign-in address and the backup age
    6 The sign-in address curl -fsS https://<your-address>/keycloak/realms/ai-firewall/.well-known/openid-configuration The issuer starts with your public address
    7 The console is closed curl -s -o /dev/null -w '%{http_code}' https://<your-address>/keycloak/admin/ 404
    8 The portal Sign in at https://<your-address>/admin/ Your workspaces, devices and policies are there
    9 The audit chain The chain check in the portal It verifies. A gap from the restore shows as a re-anchor, not as tampering
    10 Agents The device list in the portal Devices report again within minutes

    What agents experience after a restore¶

    • Computers enrolled before the backup reconnect with their existing keys. Nothing to do.
    • Computers enrolled after the backup are refused at first. The agent then drops its key and joins again by itself with its enrolment key. This works only if the enrolment keys did not change, which is another reason to restore the original .env.
    • Audit events between the backup and the failure are lost on the server, unless agents still hold them and send them again. The gap is recorded as a re-anchor.
    • Changes made in the portal after the backup (policies, groups, administrators, sign-in accounts and one-time codes) are lost and must be done again.
