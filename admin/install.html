    Install the server¶

    This page takes you from an empty Ubuntu server to a working AI Firewall server. Read Prerequisites first.

    Step 1. Prepare the server¶

    Connect over SSH and become the administrator:

    ssh <user>@<server-address>
sudo -i
cd <folder that holds install.sh>
chmod +x ./install.sh

    If you copied install.sh from a Windows computer

    A script saved with Windows line endings can fail silently on Linux. Convert it before you run it:

    sed -i 's/\r$//' install.sh

    Step 2. Install Docker and the aifw command¶

    bash install.sh

    The script:

    1. installs Docker Engine and the Docker Compose plugin, if they are missing;
    2. asks for the registry access name and token from your welcome email (what you type is hidden) and checks them at once;
    3. downloads the setup tool and installs the aifw command.

    Check that it worked:

    aifw --version

    To install a specific version of the aifw command, set AIFW_VERSION when you run the script, for example AIFW_VERSION=<version> bash install.sh. By default the script takes the newest published version. To upgrade a server that already works, do not run the script again: use aifw upgrade. All the settings of the script and its error messages are on The installer script. Every aifw command is described on aifw commands.

    Step 3. Check the server (optional, recommended)¶

    aifw preflight

    It checks the processor, memory and disk, that the needed ports are free, that systemd is present and that the server can reach the software registry. It changes nothing. A problem shows up here instead of half way through setup. Run it before a non-interactive installation, when nobody watches the questions.

    Step 4. Run setup¶

    Setup creates and starts everything. You can run it in two ways.

    Interactive. Setup asks the questions one by one and shows a summary to confirm before it changes anything:

    aifw setup

    Non-interactive. Setup reads the answers from a file, so an installation is repeatable:

    aifw setup --answers /opt/ai-firewall/answers.json

    Unknown keys in the file are rejected with an error, so a typing mistake fails loudly. Passwords and tokens are never part of this file. They are always generated for your server.

    To see the whole plan without changing anything:

    aifw setup --check

    Whichever way you run it, setup goes through eight phases: server check, server preparation, your answers, configuration and generated secrets, download and start, secure web access, sign-in service set-up, and the final sign-in details and backup set-up. It reports what it created and what was already in place.

    Running setup again is safe

    Each step looks at the server before it changes anything, so a second run changes only what has drifted. Your previous answers are offered again. Use aifw setup --check first on a live server: it shows what would change and changes nothing.

    Before you change a basic answer

    Setup does not change the public address, the version or the administrator e-mail of a server that is already set up. It stops and names the setting. If one of them is wrong and the server is not in use yet, restore the snapshot taken before the installation, then run setup again. To change the version, use aifw upgrade. You can change how HTTPS is handled by running setup again. Do not rely on setup to apply a new license file to an existing server. Take a snapshot of the server before you change anything.

    The answers¶

    Answer Prompt What it is
    flavor Server type standard for a normal installation.
    publicUrl Public address The full https:// address of the server. No path, no trailing slash.
    version Version The exact version to install, for example 2.2.7. Not latest.
    authMode Emergency token field on the sign-in page compat: the sign-in page has the single sign-on button and an emergency token field (recommended). keycloak: single sign-on only.
    licenseBlobPath License file path The full path of the .license file on the server.
    adminEmail Admin email The first administrator. A temporary password is made and shown once at the end.
    workspaceId First workspace name main, unless you need another name.
    adminSshSourceIp Restrict SSH to one address Optional. Lets only this address connect over SSH.
    hardenSsh (answers file only) Optional. true turns off SSH sign-in by password. Default false.
    rootDir (answers file only) Where the installation lives. Default /opt/ai-firewall.

    How HTTPS is handled¶

    One more answer decides how the server gets its HTTPS certificate. It is called HTTPS handling in the questions and tlsMode in the answers file.

    Option 1. Automatic certificates (Let's Encrypt)¶

    Choose this when the server has a public DNS name that is reachable from the internet, and you want the certificate to be issued and renewed automatically.

    Key Value
    tlsMode caddy-letsencrypt
    letsencryptEmail The contact address for certificate notices

    Port 80 must be open, as well as 443. The DNS name must already point at this server, because the certificate authority checks it during setup.

    {
  "flavor": "standard",
  "publicUrl": "https://ai-firewall.example.com",
  "version": "<version>",
  "authMode": "compat",
  "licenseBlobPath": "/opt/ai-firewall/company.license",
  "adminEmail": "admin@example.com",
  "workspaceId": "main",
  "tlsMode": "caddy-letsencrypt",
  "letsencryptEmail": "admin@example.com",
  "hardenSsh": false
}

    Option 2. Your own certificate¶

    Choose this when you have your own certificate, for example from a company certificate authority, or when the server has no public DNS name.

    Key Value
    tlsMode caddy-custom
    tlsCertPath The full path of the certificate (.pem) on the server
    tlsKeyPath The full path of its private key

    Put the certificate and key on the server before you start, at those paths, readable by the user who runs setup. Port 80 is not needed.

    {
  "flavor": "standard",
  "publicUrl": "https://ai-firewall.example.com",
  "version": "<version>",
  "authMode": "compat",
  "licenseBlobPath": "/opt/ai-firewall/company.license",
  "adminEmail": "admin@example.com",
  "workspaceId": "main",
  "tlsMode": "caddy-custom",
  "tlsCertPath": "/opt/ai-firewall/certs/server.pem",
  "tlsKeyPath": "/opt/ai-firewall/certs/server.key",
  "hardenSsh": false
}

    Option 3. Your own load balancer or proxy¶

    Choose this when a load balancer or reverse proxy in front of the server already ends HTTPS, and only plain HTTP reaches the server. This is usual in a company network or behind a managed load balancer in a cloud.

    Key Value
    tlsMode external
    lbIp Optional. The address of the load balancer, to allow it through the firewall

    Set up and start the load balancer before you run setup. Setup also writes ready-made settings for nginx and IIS that you can use. See Reverse proxy.

    {
  "flavor": "standard",
  "publicUrl": "https://ai-firewall.example.com",
  "version": "<version>",
  "authMode": "compat",
  "licenseBlobPath": "/opt/ai-firewall/company.license",
  "adminEmail": "admin@example.com",
  "workspaceId": "main",
  "tlsMode": "external",
  "lbIp": "<load-balancer-ip>",
  "hardenSsh": false
}

    Step 5. Check that it works¶

    docker ps

    All containers must show Up, and (healthy) once their start-up time has passed:

    Container What it does
    ai-firewall-caddy Handles HTTPS on ports 80 and 443 (not present when you use your own load balancer)
    ai-firewall-control-plane The server itself: devices, administration and audit. Listens on port 8090 inside the server
    ai-firewall-admin-portal The admin portal
    ai-firewall-keycloak The sign-in service
    ai-firewall-pg The database
    ai-firewall-prometheus, ai-firewall-grafana Metrics and dashboards
    ai-firewall-postgres-exporter, ai-firewall-blackbox Monitoring helpers

    ai-firewall-init-keycloak runs once when the server starts, creates the sign-in database and stops. It does not appear in docker ps. That is normal.

    From the server, ask the service if it is healthy:

    curl -fsS http://127.0.0.1:8090/health
curl -fsS http://127.0.0.1:8090/ready

    Or run:

    aifw status

    Then, from outside:

    • health: https://<your-address>/health must answer {"status":"ok"};
    • the sign-in page: https://<your-address>/admin.

    Step 6. Save the sign-in details¶

    Setup writes the sign-in details to credentials.txt in the install folder, for example /opt/ai-firewall/credentials.txt. They are also shown on the last screen. The file holds:

    • the address of the admin portal, the administrator's email and a temporary password;
    • the device enrolment key, which the agent installers use to join computers to your workspace;
    • the emergency sign-in token;
    • the monitoring dashboard password;
    • the sign-in service console account and the command to reach the console (see Sign-in and roles).

    Move every value into your password manager now, then delete the file:

    rm /opt/ai-firewall/credentials.txt

    Other secrets that the installation needs (the database password, internal tokens and the license) are generated into a file that only the administrator can read, in the install folder. Keep it on the server. Do not copy it, and never paste it into a ticket or a chat.

    Step 7. Check the firewall of the server¶

    ufw status verbose

    Only the ports for your HTTPS option (see Prerequisites) should be open. Everything else is blocked.
