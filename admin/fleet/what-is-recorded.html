    What the workspace records¶

    Protection happens on the employee's computer. The agent checks each request there, before it leaves. The private values that it finds are not collected: the agent replaces them on the computer before anything is sent to the workspace.

    The workspace does receive a record, and you should tell your employees what it contains. This page lists it in plain words, for version 2.2.8.

    What reaches the workspace¶

    What Where you see it How long Notes
    Audit events. One for each request the agent scanned, including requests where it found nothing: the time, what it did (pass, log, mask, block), the host and path, the types of data found, the computer, and the size Audit, tab Events 90 days Each event carries a preview. See The preview
    Conversations. The messages the employee sent, with the detected values replaced Audit, tab Conversations 30 days Only when Trace content is full, which is the default. See How much of a conversation is kept
    A status report about every 30 seconds: host name, operating-system user name, machine ID, versions, protection state, counters Devices, the device page Updated as it arrives See Who the audit record names and The status report and the list of sign-in names
    Counters. How many requests were checked, how they were handled, how long scanning took, and how the two detectors agreed AI Activity, Tenants > Capture, the device tab Capture No message text
    Agent log lines The device tab Logs Not stated On for a new workspace, at level info. A partial filter removes e-mail addresses, phone numbers, card numbers and file names. Host names and error messages go as written
    Developer tools. The tools found on the computer: their configuration file paths, the commands and arguments that start them, the names (never the values) of related environment variables, and risk flags Dashboards > Dev Tools The paths start in the user's home folder, so they contain the operating-system account name. There is no switch to turn this off. The report can also carry a verdict on which MCP servers and skills your policy does not allow. See AI coding agents
    What administrators changed: who, when, which action Tenants > Audit Not stated See Audit and evidence

    The status report and the list of sign-in names¶

    Every enrolled computer sends a status report about every 30 seconds. It carries the host name, the operating-system user name, a machine ID, versions, the protection state and counters. The device page shows the latest report.

    The server also keeps a list of the sign-in names that computers report in the workspace, with when each name was first and last seen on each computer. It uses the list for policies for people. The server writes the list whatever you set for who audit records name, and nothing deletes it. The portal has no screen for it. It is available only through the API.

    Who the audit record names¶

    An audit event carries either the person or only the computer. The setting is auditIdentity.employeeNoticeAcknowledged on the Config tab.

    • Off (the default for a new workspace). The event names the computer, as device:<device ID>, and no person. The portal chip on Overview reads Audit: device only.
    • On. The event carries the operating-system user name of the person who was signed in. The chip reads Audit: person named.

    Turn it on only when your organisation has told its employees, and its works council where it has one, that audit records name them. The setting is your statement, not a switch the agent can change.

    This setting is read by agents from 2.2.8. Older agents named the person whenever the computer was enrolled, and rows they wrote stay as they were for up to 90 days.

    Even with the setting off, the workspace knows the user name

    Device only is not anonymous. Every enrolled computer sends its operating-system user name and its host name in its status report, and the device page shows them as OS user and Hostname. The people who can open the Devices page can see which user is on which computer. Say this in your privacy notice.

    Because of the setting, these screens look different when it is off:

    • The User column in Audit is empty.
    • Users, Risk and the Person grouping in Conversations show nothing for people. The Users page may explain the empty list by saying that older agents do not send the user e-mail yet. With this setting off, the setting is the reason.
    • Alerts about people name the computer instead.

    The preview¶

    Each audit event carries a preview: the first 200 characters of the message, with the values the agent detected replaced by a tag such as [EMAIL], and about 50 characters of context around each detection. It does not show the detected value.

    The preview is only as good as the detectors

    The agent replaces a value only where a detector found it. A name, an address or a number that no detector recognised stays readable in the preview, to everyone who can open Audit. The same holds for a find below a detector's cutoff (see Detection and thresholds).

    Setting Trace content to metadata removes the preview and the context from audit events.

    How much of a conversation is kept¶

    The setting Trace content, field mode, applies to the whole workspace. A group or a single computer can only make it narrower.

    Level What the workspace keeps
    full (the default when nothing is set) The messages the employee sent, with detected values replaced, in Conversations
    masked No conversations. The 200-character preview stays in the audit events
    metadata No conversations and no preview: only the types and counts

    In masked and metadata, the agent does not send conversations at all, and Conversations says that the workspace keeps no conversations. A change is not applied to what was stored before.

    The reply of the AI service is never sent. Conversations shows only the employee's side. Earlier replies that a later request carries as history are included in that request, so they are recorded with it.

    A conversation message is labelled with how it was recorded:

    • "As it left the device — detected values already replaced."
    • "A copy for the record, with detected values replaced. The AI service may have received some of these values."
    • "Not recorded. This message was not fully scanned, so its text was not kept in this record. The AI service still received it."
    • "Not recorded. This message could not be recorded with its detected values replaced…"

    What is not stored¶

    • The detected values. The portal has no "show the original".
    • The full prompt. It stays on the computer.
    • The reply of the AI service.
    • The content of images. For an image, Audit shows a redaction map only ("Image not retained").
    • File names of attachments. A file is shown as [document].<extension>, with its type and size. A file name with an extension the product does not know shows only as [document]. Query strings are dropped from addresses.
    • File hashes.
    • The words of your keyword list. A record says that a keyword matched, never which word.

    Be careful with two things: file names are replaced in the path of an upload, but the path of a document on the device appears in the developer-tool list as described above, and agents older than 2.2.6 could keep raw text and file hashes. Those rows age out after 90 days.

    Detection and thresholds¶

    The agent has two kinds of detector.

    • The name detector (for person names, organisations, addresses): a find below its cutoff is dropped. It is not replaced and is not recorded anywhere. The cutoff depends on the model. For the default model it is 0 for person names and 0.5 for most others, not a general 80%. You can set it per type in dlpThresholds.
    • Patterns (for example card numbers): a find below 0.4 is recorded, with its type and its tag in the preview, but it is not replaced or blocked in Replace and Block. The original value is sent on to the AI service.

    What is not covered by a switch¶

    There is no setting that makes an agent send the text of a prompt to the server. The learningMode and evalCapture switches that the editor still shows record no prompt on current versions.

    Request counts and details such as host and path, without any text, can be sent for the Capture tab. That is off by default: it needs capture.metadataEnabled.

    What the server itself fetches¶

    By default the server downloads public vulnerability advisory data (the OSV lists for npm and Python packages) about a minute after it starts and then once a day. It is a download only. The setting ADVISORY_REFRESH=off on the server stops all contact and uses only the files already in its folder. If your servers must not reach the internet, set it.

    Limits of the screens that use this data¶

    • Users, Risk and Reports are worked out from the newest 500 audit events of the workspace, whatever window you choose, and the page gives no warning. On a busy workspace a 30-day or 90-day report covers much less than its title. Do not present them as complete.
    • Risk is not a score out of 100. It adds 5 for each block, 2 for each mask and 0.5 for each log.
    • Audit shows the last 90 days. There is no export on the Events tab.
    • The agent log lines and the counters that the server keeps are meant to be deleted after 30 and 90 days, but nothing on the server does it. Treat their retention as not enforced. Ask your ScienceSoft representative.
